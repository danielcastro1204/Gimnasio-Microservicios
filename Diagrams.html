4. Secuencia: Validación Síncrona REST (Class ↔ Trainer)

Única comunicación síncrona entre microservicios: class-service valida contra trainer-service antes de programar una clase.

                sequenceDiagram
                    autonumber
                    actor Cliente
                    participant MS as Class Service
                    participant TS as Trainer Service
                    participant DB as classdb

                    Cliente->>MS: POST /api/classes
                    MS->>TS: GET /api/trainers/{id}/exists

                    alt Trainer exists
                        TS-->>MS: 200 OK
                        MS->>DB: save(newClass)
                        DB-->>MS: entity saved
                        MS-->>Cliente: 201 Created
                    else Trainer missing
                        TS-->>MS: 404 Not Found
                        MS-->>Cliente: 409 Conflict
                    end

6. Secuencia: Cola de Trabajo con Dead Letter Queue (pagos)

Cola punto a punto pagos-queue con reintentos (Spring Retry, backoff 1s/2s/4s); al agotarse se rechaza sin reencolar y el mensaje cae en pagos-dlq.

                sequenceDiagram
                    autonumber
                    actor Cliente
                    participant MS as Member Service
                    participant PQ as pagos-queue
                    participant DLQ as pagos-dlq
                    participant DB as memberdb (tabla pagos)

                    Cliente->>MS: POST /{miembroId}/payments
                    MS->>DB: save(Pago PENDIENTE)
                    MS-->>Cliente: 202 Accepted
                    MS-)PQ: publica PagoEvent

                    PQ-)MS: PagoConsumer.procesarPago
                    alt Pago exitoso
                        MS->>DB: marcarExitoso(pagoId)
                    else Falla (simularFallo=true)
                        loop hasta 3 intentos (backoff 1s/2s/4s)
                            MS-->>MS: reintenta procesarPago
                        end
                        MS--)DLQ: reject sin reencolar (agotó reintentos)
                        DLQ-)MS: PagoDeadLetterConsumer
                        MS->>DB: marcarFallido(pagoId, detalle)
                    end

                    Cliente->>MS: GET /payments/{id}
                    MS-->>Cliente: 200 OK (EXITOSO | FALLIDO)

class-service produce cada cambio de ocupación en el topic ocupacion-clases (key = claseId, mantiene el orden); notification-service lo consume y mantiene el "dashboard" en tiempo real.

9. Recuperación ante fallos con el log de Kafka (checkpoints)

En paralelo al Stream Processor, un consumidor propio reconstruye el historial y guarda un checkpoint (topic, partición, offset) en la misma transacción que el dato. Al reiniciar, retoma en checkpoint + 1; sin checkpoint, reproduce el log completo.

                sequenceDiagram
                    autonumber
                    participant T as Topic datos-entrenamiento
                    participant REC as RecuperacionService
(consumer assign + seek)
                    participant DB as analyticsdb (archivo)
kafka_checkpoints /
entrenamientos_registrados

                    Note over REC,DB: Arranque normal
                    REC->>DB: cargarCheckpoints("datos-entrenamiento")
                    DB-->>REC: {particion: últimoOffset, ...}
                    REC->>T: seek(particion, últimoOffset + 1)
                    T-)REC: poll() -> nuevos registros
                    REC->>DB: TX: save(registro) + save(checkpoint)

                    Note over REC,DB: Falla el proceso (se cae o error)
                    REC--xREC: crash / excepción
                    Note over REC: Se reinicia el hilo

                    REC->>DB: cargarCheckpoints (recupera el último guardado)
                    REC->>T: seek(particion, checkpoint + 1)
                    Note right of T: No se pierde ni duplica:
restricción única (topic, partición, offset)

                    Note over REC,DB: POST /recovery/reset (simula pérdida total)
                    REC->>DB: borra datos y checkpoints
                    REC->>T: seek al primer offset disponible
                    T-)REC: reproduce el log completo
                    REC->>DB: reconstruye el estado desde cero
